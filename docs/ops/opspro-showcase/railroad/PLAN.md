# Showcase plan: the Juniper Falls & Northern

Stage 1 output for the Operations Pro showcase. Stages 2 to 4 build from this file alone, so it names every object. The brief's rules apply in full and are not repeated here; this file adds what was proved or decided.

Folder: `plugins/operations-pro/examples/showcase/` (no reason was found to put it anywhere else). Files: `operations/` (the six XML files, `buildstatus/`, `backups/`), `build/` (replayable JSON batches, below), `build.py`, `PLAN.md`, `RESULTS.md`, `GUIDE.md`, and `tests/test_showcase.py` in the plugin's test folder.

## 1. What stage 1 proved on throwaway railroads (real JMRI 5.16, plugin actions only)

| Proved | Consequence for the design |
|---|---|
| A folder with no Operations files starts as an empty railroad; `servers/blank/` already holds JMRI's default car types (Boxcar, Caboose, Hopper, Tank Oil and so on), so `add_car_type` of a default name is refused | The skeleton adds only new types (`Buffer`, `Coilcar` if absent) and uses JMRI's names otherwise |
| `ops_why_not` router: "two trains through staging Hop"; JMRI delivered the car Mill → Hop (staging, Routed on) → Far Spur over two sessions. A default E car asked for the Routed hop fails D16/E7 | R05 and the staging half of R08 share one hop track. Routed on staging is safe when the arriving train's only staging-bound cars are routed ones |
| Two trains sharing a staging hop alternate sessions (the second fails A7 while the first's car waits on it) unless the hop has planned pick ups (`ignore_used_percent` 100); with it both build in one session | Every staging track that is both a terminal and a departure gets planned pick ups 100 |
| A turn Turn A → Mill → back with `allow_return` departs Turn A and terminates on Turn B, then the reverse next session | R19 uses two tracks with the train on both lists |
| `Mill-(yard)` and `Mill-(industries)` print as "Mill" on the manifest, and a road train will not move a car between them (same split name, D4) | R16's pair is worked by a switcher whose route is the two locations |
| A spur `Freight House` beside `Freight House-(2)` (scheduled): the E car went to the first, the Crates car to the second, and the manifest printed "Freight House" for both set outs | U10 as the brief describes it works; the paperwork claim is true for track names too |
| A custom load with two receiving spurs at equal moves went to whichever sorted first by location id, not the nearer one | Every custom load in the showcase has one receiver, except where a case wants several (U06, U08, U09, R09) |
| A train with no work still builds ("Partial 0/n") | "Every train builds" holds even for trains whose cars arrive next session |

Probe scripts: `scratchpad/probe/t1.py`, `t2.py`, `t3.py` (not shipped).

## 3. The railroad

**Name:** Juniper Falls & Northern (JF&N). Invented, as are every town, industry and road. The banned-word scan is a case-insensitive substring match, so no showcase file may contain the owner's layout name even inside another word: in particular the common English word for a graph or table of figures (c-h-a-r-t) is off limits in every showcase file, this one included.

**Map.** Mainline west to east: West Staging, Carrow (hub yard), Brae, Dunmere, Ferris Junction, Linden, East Staging. South branch from Carrow: Hollis Mill, Oakhaven. North branch from Ferris Junction: Pell Creek-(yard), Pell Creek-(industries), Northwood. Carrow jobs: Sawyer (switching town), Kessock (classification yard), Fiddle (fiddle yard). 15 locations counting the hyphen pair as two, 18 trains, about 110 cars, 7 locomotives. The brief said about 12/16/100: the extra locations are forced by the same-location rule (shipper and receiver of a routed load cannot share a location unless a switcher moves them) and by one job per switcher; the extra trains are the second halves of pairs (two swap trains, two kessock trains, two hop trains).

**Isolation rules** (the reason no car can serve two cases):

1. Each custom load has one receiving schedule line (exceptions above). Custom-load cars carry road `JFN` and start on infrastructure yards; the load steers them.
2. Each default-load case has its own road, listed in `Include` on every track that case owns and on nothing else. Infrastructure yards take roads `JFN` and `WNDR` only. Staging tracks take all roads and filter by train lists.
3. Default-load case cars start on a track their case owns, never on an infrastructure yard (so no car sits on a track that refuses its road).
4. Trains carry every car type (what `add_train` gives) and every road unless a row below restricts them; the type lists on tracks do the fencing.
5. Every staging track names its trains in Pick ups and Set outs; a train from staging is `engines: "0"` unless a case says otherwise.
6. A turn cannot set a car picked up at its origin back at the origin (D4), so cars that start at a turn's origin are expected at an intermediate stop.

**Car types** (JMRI defaults unless marked new): Boxcar, Covered Hopper, Hopper, Gondola, Flatcar (JMRI: `Flat`; use whatever the blank file holds), Coal, Coilcar, Reefer, Stock, Tank Oil, Tank Gas, Tank Veg, Tank Food, HopGrain, Caboose, Baggage, Passenger, plus new: `Buffer`, `Diner`, `Observation`. Loco type `Diesel`.

**Roads:** `JFN` (home road), `WNDR` (U03 wanderers), `SWPX` (U07), `MODX` (U12), `TRNX` (R19), `HZMX` (U22), `KRNX` (U13 kernel), `FRHX` (U10), `OUTX` (R17), `RIPX` (U24), `KESX` (R11), `PELC` (R16), `NWRX` (U21), `SWYX` (R12), `WSTX` (R15), `CNXX` (R18), `XFRX` (R07), `GTEX` (R06), `OAKX` (R10), `TEMX` (U16), `BOXX` (R08 default car), `OILX` (R13), `FLYX` (U18), `LCLX` (U22 LCL).

**Custom loads** (type): Feed (Covered Hopper, U01), Canned (Boxcar, U02), Lumber (Boxcar, U03), Semolina (Boxcar, U04), Machinery (Boxcar, U06), Parts and Tools (Boxcar, U08), Grain (Covered Hopper, U09), Crates (Boxcar, U10), Flour (Boxcar, U11), Barley (HopGrain, U21), Girder (Flatcar, U22), Produce (Reefer, R02), Pipe (Gondola, R03), Coil (Coilcar, R04), Salt (Covered Hopper, R05), Boxes (Boxcar, R08), Stone (Hopper, R09), Wheat (Covered Hopper, R10), Bricks (Boxcar, R16).

**Car numbering:** `JFN` cars of a U case are numbered `<code>01..` (U01 → JFN 101, U13 → JFN 1301); R cases `5<code>01..` (R02 → JFN 5201). Case-road cars are numbered 1 upward. Every car, track, location, schedule, train and route comment starts with its code, for example `[U07]`; infrastructure objects start with `[INFRA]`.

## 6. Batches (stage 3)

Each batch is one file `build/<nn>_<batch>.json`: a JSON list of steps, each `{"plan": [actions]}` or `{"deliver": {"car", "location", "track"}}`, applied in file order. `SESSIONS` is built once per module (`setUpModule`): `CHAINS = 3` copies, each run through `SESSIONS_PER_CHAIN = 3` consecutive `run_worker(..., {"build": True, "terminate": True, "save": True}, keep)` calls, copying the saved files forward each time (the pattern of `scratchpad/probe/t1.py`). The chains run in parallel (`ThreadPoolExecutor`, as `ops_jmri._sample` does). A deterministic case asserts in every chain; a random one (U08, and any row whose Expected says "record") asserts over the union, and `RESULTS.md` records the counts. Experiments are not tests: stage 3 runs each once on a copy and writes the tool's answer into `RESULTS.md` and the guide.

Nondeterminism known in the design: staging destination choice (none of the cases let a custom load fall to staging), generated-load spur choice (U06 cars may go to either depot: assert the set), schedule random (U08), and the aggressive-mode copies (U12 uses `ops_build_check`'s set comparison). `ops_why_not` with JMRI installed runs four real builds for E9/D3/D9: tests that read a gate's `status` must pass `real_build` false unless the gate is one of those, to keep them fast.

Run cost: one JMRI start is about 15 s; a chain of three sessions about two minutes; the module about three minutes on this machine.
