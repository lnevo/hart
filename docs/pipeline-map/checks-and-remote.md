# Checks and the Windows compute box

How `./tools/check.sh` decides what to run, and how heavy jobs go to the Windows box instead of the Mac.

## check.sh

Run `./tools/check.sh` before any commit that changes tables or signals. CI runs it on every PR, without the portal build.

- **Where the checks are listed.** The read-only checks are steps in one manifest, `tools/pipeline/checks.toml` ([ADR-037](../../wiki/decisions/ADR-037-one-step-manifest.md)). `check.sh` asks `python3 tools/pipeline/manifest.py jobs check` for them: the `static` group runs as the one `static` job, in file order, and a step with no group (`public-text`, `ruff`, `portal`) is a job of its own. `tools/ci/docs_checks.sh` runs the steps marked `docs_only`. A manifest that does not load, or a list with no check, stops both before any job runs (exit 2, with the loader's error); `check.sh` never ends `ALL PASSED` with no job run, and a `CHECK_ONLY` that matches nothing fails. Two conditions stay in `check.sh`, keyed on a step's name: the `panels` step gets `--full` when no job is skipped, and the `portal` job runs only off CI and where its inputs changed; `check.sh` stops if either step is missing.
- **Adding a check.** Add one `[[step]]` to `checks.toml` with `group = "static"`: `name` (the job name stamps key on), `runner = "check"`, `cmd`, `domain`, `label` and `desc` (the map box's name and text), and `inputs` and `outputs`. Add `docs_only = true` if a docs-only change can break it. Run `python3 tools/pipeline/manifest.py check`; the file's header lists every field. A step with no group is a job of its own and also needs a `BY_KIND` declaration in `tools/audit/check_stamps.py` (a test says so). Then run `make map`: the map draws the step's script as a box, with a link from each input, to each output and to `tools/check.sh` labelled `check <name>` (its manifest lane, `tools/pipeline/map_lane.py`, marked `"gen": "manifest"`), and the `pipeline-map` check fails until the graph is rebuilt. An input or output must already be a box of the map. Do not edit those boxes and links in `pipeline_map.json` by hand: the next build overwrites them and `--check` names each one that differs. Links from code into the script (imports, calls) stay hand-kept.
- **Docs-only changes.** When every path the checkout changes (the branch against its merge base with `origin/main`, plus uncommitted and untracked files) is Markdown docs by `tools/ci/changed_kind.py`, the rule CI uses, `check.sh` runs only the quick docs checks (`tools/ci/docs_checks.sh`, the list CI runs) and stops. The list includes the few unit tests that read Markdown in the repo (`test_name_copies` and the speed matching runbook test); `tools/audit/tests/test_check_docs_only.py` keeps it in step with the stamp declarations. The portal build is not run on this path, as in CI: it stays with the website deploy (owner, 2026-11-24). Its first line says so, it records no stamps, and it ends `DOCS CHECKS PASSED`, not `ALL PASSED`: it is not a pass of `check.sh`. `FULL=1`, `CI`, `CHECK_ONLY`, `CHECK_AUDIT`, `HART_TABLES` and `PORTAL_CHECK=1` take the normal path, and so does a checkout with no merge base (a shallow clone), with the reason on the first line.
- **Portal build.** It is skipped when the branch changes no site input. `PORTAL_CHECK=1` runs it anyway.
- **Built views.** The pipeline map pages (`docs/pipeline-map/index.html`, `www/library/pipeline-map.html`) are not committed ([ADR-036](../../wiki/decisions/ADR-036-generated-views-not-committed.md)). The `pipeline-map` check (`build_pipeline_map.py --check`, in the static job and the quick docs checks) draws both in memory and fails on a stale graph or a page that does not build; it compares no bytes. `make map` writes them to look at; the site build writes its own copy.
- **Job stamps.** Each job runs under a trace hook (`tools/audit/traced.py`) that records the files its Python processes opened, probed and listed. A job whose recorded reads are unchanged since its last pass prints `<job>: current, skipped` and is not run again, so an edit re-runs only the jobs that read the file. A job that ran bash, node or a writing git falls back to the folders `tools/audit/check_stamps.py` declares for it. `python3 tools/audit/check_stamps.py why <job>` says why a job ran. A manifest job's key holds a digest of its own `checks.toml` entries (all of the `static` group's for `static`), so editing one step reruns its job and no other; an edit to `check.sh` or `tools/pipeline/manifest.py` reruns every job. Every job's stamp is checked in one `check_stamps.py current-batch` process before any job starts, and a current job is never started; when that process fails, every job runs, none records a stamp, and the output says why. A unit job whose tests skipped records its stamp too, with each skipped test's id and reason in its key; what a test skips on (a tool `shutil.which` does not find, a package, a file, a git ref) is an input like a file it read, so the job runs again when that changes. Stamps are in `<main checkout>/.cache/hart/check-stamps`, shared by every worktree and by `make remote`. `make panels` steps are stamped the same way (`python3 tools/schematic/panel_stamps.py why <step>`).
- `FULL=1` runs everything and records the stamps; with `CI` set nothing is skipped or recorded, except in the two CI modes below. `CHECK_ONLY=<regex>` runs only the jobs it matches.
- **CI skips what main covered.** Main's push run runs every job with `CHECK_RECORD_TO` and saves the stamps of the jobs that passed in the Actions cache, keyed on its commit. A pull request run restores the stamps for its merge base and runs `check.sh` with `CHECK_SKIP_FROM`: a job whose inputs are byte-identical to that pass prints `<job>: current on main <sha>, skipped`, and every other job runs. `tools/ci/stamp_gate.py` runs everything, and logs why, when the stamps are missing or for another main commit, the runner image, Python, git or bash differs (not the image build number, which varies between runners), the plugin pin changed, the change touches `check.sh`, `check.yml`, `tools/pipeline/manifest.py` or the stamp code (not `checks.toml`: each job's key holds its own entries), the pull request has the `full-ci` label, or one of its commit messages has `[full-ci]` (add the label, then re-run the job). Jobs that cannot be stamped (a check that printed `SKIPPED`) and jobs whose key holds HEAD (`static`, `portal` and `unit-hosts test_redeploy_commit`) always run. A weekly scheduled run checks main in full.
- **Panels.** The static job checks every output drawn from the schematic with one line, `build_panels.sh --check` (`panels`): the steps of `make panels CHECK=1`, not a copy of them. It runs bash, so the static job's stamp falls back to its declaration. It shares its step stamps with `make panels`; CI, `FULL=1` and an audit run pass `--full`. With `HART_TABLES` set its stamps are off, every step runs, and the table steps read that file. Without the plugin it fails even with `SCHEMATIC_REQUIRED=0`: the `schematic` step (`publish_draft.py --check`) has no SKIPPED path.
- **Pyflakes.** The `ruff` job runs `tools/audit/check_ruff.py`: ruff's F rules only (undefined and unused names, unused imports, f-strings without placeholders), no style or formatting rules. `ruff.toml` at the root lists what is excluded (vendored code, `archive/`, the parked features, Jython scripts that do not parse as Python 3) and the per-file ignores (F821 in Jython scripts, whose names come from JMRI or from `execfile`; files other branches are changing, to remove after they merge). Ruff is pinned in `requirements.txt`; the check uses that version from the main checkout's `.venv`, else from PATH, and fails when neither has it. CI installs the pin (`check_ruff.py --pin` prints it), and `make remote` installs each pinned version once with uv into `~/.cache/hart/ruff/<version>` on the Windows box and puts it first on PATH for that run; a failed install there is a warning, and the ruff job then fails with the reason. On the Mac: `.venv/bin/pip install -r requirements.txt` in the main checkout. `.claude/hooks/check_after_edit.py` runs the same check on each `.py` file an agent edits (a file git ignores is skipped, as the whole-repo run skips it): findings block the edit, and a missing ruff is one line that does not block. The stamp falls back to its declaration (every `.py`, `ruff.toml`, `requirements.txt` and the `.gitignore` files), since ruff is not Python.
- **No plugin, no pass.** `check.sh` and `make panels` set `SCHEMATIC_REQUIRED=1` unless it is already set, as CI does: a schematic check that cannot load the schematic-maps plugin fails instead of printing SKIPPED. `SCHEMATIC_REQUIRED=0` lets those checks skip. A job that still printed SKIPPED (the owner's plan file is not on the machine, say) is named on one line at the end of the output.
- Logged times: a warm local run takes about 40 s, a full run 2 to 5 min. Grep earlier output (`--- job (Ns)`) before re-running just to time it.

## make remote

`make remote CMD="./tools/check.sh"` (or `tools/hosts/win_run.sh -- <cmd>`) runs a pushed branch on the Windows box's WSL. `.wslconfig` there caps it at 8 of the box's 16 threads, and each run gets its own worktree, so several at once are fine.

- Use it for a full `check.sh`, test suites and panel rebuilds. Iterate on single tests locally.
- A command with `$` in it goes through `tools/hosts/win_run.sh -- bash -c '...'`, because make expands `$`.
- Exit 3 means the operating flag is set and the box is down: run it on the Mac.
- Never use it for `panelpro-test`, screenshots or deploys.
- When the Mac is busy (load above about 8, or several sessions running checks), run `make remote` in the background beside Mac work, and have subagents run their full checks and suites through it.
- The Mac has 8 cores. Keep CPU-heavy local work to about 2 jobs at a time per session.
