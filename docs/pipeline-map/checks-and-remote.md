# Checks and the Windows compute box

How `./tools/check.sh` decides what to run, and how heavy jobs go to the Windows box instead of the Mac.

## check.sh

Run `./tools/check.sh` before any commit that changes tables or signals. CI runs it on every PR, without the portal build.

- **Where the checks are listed.** The read-only checks are steps in one manifest, `tools/pipeline/checks.toml` ([ADR-037](../../wiki/decisions/ADR-037-one-step-manifest.md)). `check.sh` asks `python3 tools/pipeline/manifest.py jobs check` for them and runs each step as a job of its own, named after the step (stage 4b): the `static` group's steps ahead of the unit tests (the `panels` step as one `panels-<step>` job per step of `tools/pipeline/panels.toml`, queued first, the slow `panels-schematic` and `panels-cats` ahead of the rest), the steps with no group (`public-text`, `ruff`, `portal`) after them. `tools/ci/docs_checks.sh` runs the steps marked `docs_only`. A manifest that does not load, or a list with no check, stops both before any job runs (exit 2, with the loader's error); `check.sh` never ends `ALL PASSED` with no job run, and a `CHECK_ONLY` that matches nothing fails. Two conditions stay in `check.sh`, keyed on a step's name: the `panels-*` jobs are queued first, and the `portal` job runs only off CI and where its inputs changed; `check.sh` stops if `panels-tables` (which the deploy gate reads) or `portal` is missing.
- **Adding a check.** Add one `[[step]]` to `checks.toml` with `group = "static"`: `name` (the job name stamps key on), `runner = "check"`, `cmd`, `git` (the git refs its stamp key holds: start with `["head", "base"]`), `domain`, `label` and `desc` (the map box's name and text), and `inputs` and `outputs`. Add `docs_only = true` if a docs-only change can break it. Run `python3 tools/pipeline/manifest.py check`; the file's header lists every field. A step that runs a program the trace cannot see (bash, ruff) falls back to every file (`MANIFEST_CHECK`) unless `BY_KIND` in `tools/audit/check_stamps.py` declares what it reads. Then run `make map`: the map draws the step's script as a box, with a link from each input, to each output and to `tools/check.sh` labelled `check <name>` (its manifest lane, `tools/pipeline/map_lane.py`, marked `"gen": "manifest"`), and the `pipeline-map` check fails until the graph is rebuilt. An input or output must already be a box of the map. Do not edit those boxes and links in `pipeline_map.json` by hand: the next build overwrites them and `--check` names each one that differs. Links from code into the script (imports, calls) stay hand-kept. `check.sh` itself runs no read-only check outside that list (`test_pipeline_manifest.CheckShRunsOnlyTheManifestTest`).
- **Declared reads.** After a manifest job's traced pass, the stamp helper takes the repo files its Python processes read (each job is one step) and prints a `WARNING: stamp audit:` block under the job's `--- stamps` heading for each file its step does not declare in `inputs`, `quiet_inputs`, `outputs` or `programs`. Only code is left out: a file the trace saw imported, run as a script or shown in a traceback (its `c` lines). A `.py` file or a file under `tools/` that a check reads as text (`jmri_additions_page.py` reading `signal_coordinator.py`, `levels_page.py` reading `tools/anyrail/levels`) is audited like any other read. A read the map should not draw, such as `tables.xml` read through hartlib, goes in `quiet_inputs`. A check that walks a folder by design (`public-text`, `name-copies`, `ai-speak`, `agent-docs`, `data-readers`, `hand-tables`, `py-sizes`, `pipeline-map`, `portal`) lists its script's own scan list there as globs (the script's `SCAN_GLOBS`, kept equal by `tools/audit/tests/test_manifest_scans.py`); a glob must match a tracked file, and `**/*` is refused unless the step's `reads_all` says why the script reads every file (only `public-text` does). `python3 tools/audit/check_stamps.py audit [job]` prints the full list again from the job's last stamp, against the manifest as it is now (exit 1 with warnings, 2 when it cannot audit). The `panels-<step>` jobs are not audited: `panels.toml`'s inputs are the map's edges, not every file a step reads, and each job's stamp log says so. No skip changes because of a warning. A local run, a pull request run and main's push run only warn, so a new undeclared read is seen before it blocks anyone; an audit run (`CHECK_AUDIT=<folder outside the checkout>`) and the weekly full run (`CHECK_AUDIT_FAILS=1`, which records into a folder nothing saves) fail the job instead, record no stamp for it, and name the passing manifest jobs they could not audit (a check that printed SKIPPED, or one not stampable now); such a run that audits no manifest job fails, and one that records nothing (CI without `CHECK_RECORD_TO`) is refused. A job with no stamp yet is audited from its own trace in that run. An audit that cannot run prints `STAMP AUDIT FAILED`, which fails the job where a warning would (ADR-037 stage 4c).
- **Docs-only changes.** When every path the checkout changes (the branch against its merge base with `origin/main`, plus uncommitted and untracked files) is Markdown docs by `tools/ci/changed_kind.py`, the rule CI uses, `check.sh` runs only the quick docs checks (`tools/ci/docs_checks.sh`, the list CI runs) and stops. The list includes the few unit tests that read Markdown in the repo (the agent front-matter test, the speed matching runbook test, test_orient on `wiki/projects/` and test_export_track_lengths on `docs/jmri/TRACK_LENGTHS.md` among them): `tools/ci/docs_unit_tests.py` makes them from the stamp declarations on `docs/` or `wiki/` in `tools/audit/check_stamps.py`, less those it leaves out with a reason, and a list with no unit test stops the run. The list of left-out tests stays short: a whole suite that reads docs only in part stays out (owner, 2026-11-24). The portal build is not run on this path, as in CI: it stays with the website deploy (owner, 2026-11-24). Its first line says so, it records no stamps, and it ends `DOCS CHECKS PASSED`, not `ALL PASSED`: it is not a pass of `check.sh`. `FULL=1`, `CI`, `CHECK_ONLY`, `CHECK_AUDIT`, `HART_TABLES` and `PORTAL_CHECK=1` take the normal path, and so does a checkout with no merge base (a shallow clone), with the reason on the first line.
- **Light changes** (owner, 2026-11-26). `changed_kind.py` says `light` when every changed path is docs as above or a data file (`.json`, `.csv`, `.tsv`, `.txt`, `.md`) and, for each data file: it is not code or configuration (`.py`, `.js`, `.sh`, `.ps1`, `.php`, `.toml`, `.xml`, anything under `jmri/`, `cats/`, `.github/`, `.githooks/`, `.claude/`, `.cursor/`, `Makefile`, an `AGENTS.md`), no path of `tools/hosts/live_paths.txt` covers it, a box of `pipeline_map.json` covers it and no generator writes that box, every `check.sh` job whose step declares it (`checks.toml` inputs, quiet_inputs, outputs, programs) is in the `static` group or on the docs path, and no unit job's stamp declaration (`check_stamps.py` BY_KIND, EXTRA, RUNS_JOBS) covers it. The first rule a path breaks is the reason in its `full:` line; declarations that cannot be read make it full. `check.sh` then runs `tools/ci/light_checks.sh`: `make static`'s jobs plus any `panels-*` job that declares a changed file (through `check.sh` with `CHECK_ONLY`, so with its stamps), then `docs_checks.sh` (public-text and the docs unit tests among them); it ends `LIGHT CHECKS PASSED`, not `ALL PASSED`. CI runs the same script on the pull request's paths, with the schematic cache and without the stamp gate, ruff, mypy or the full `check.sh`. A light change skips `make remote`. `make pr-kind` prints the verdict and reason for the branch.
  - **The pipeline map.** `pipeline_map.json` is light only when it differs from its base copy (the merge base, or `--compare` in CI) in `presets` alone, the Start menu, which only the map pages read; `build_pipeline_map.py --check` (the `pipeline-map` job) checks each preset and builds both pages. A change to any other key (a box's label or description, `updated`, any node or edge) is full: the manifest loader, `pipeline_query.py`, the map lanes, the coverage check and the tests on the real map read nodes and edges, and the declarations do not say which fields each reads.
  - **What is light today.** A data file under `docs/` or `wiki/` that no unit job's declaration names is light: the speed matching profiles no test replays (`docs/jmri/speedmatching/profile-2026-11-13/`), for example. The data checks' tests declare the masters they read (`check_stamps.SIDECAR_MASTERS`, `ENTITY_MASTERS`; `tests/test_unit_declarations.py` checks both against their sources), so an edit to a master stays full. Under `ops/`, `unit-hart-ops` and `unit-schematic` declare the folders and data files a trace of their suites saw them read (`check_stamps.UNIT_HART_OPS_DATA`; for `unit-schematic` the `schematic` panels step's crew master, `industries.csv` and publications code, which `test_panel_stamps` runs untraced), so an edit to a data file neither reads, such as `ops/hart-ops/data/car_queue.csv`, is light. Every data file under `www/` is still full: the `portal` job reads `www/**`, and `unit-portal` declares `www/**` because its node and bash run untraced. A change of docs and the map's presets is light.
- **Portal build.** It is skipped when the branch changes no site input. `PORTAL_CHECK=1` runs it anyway.
- **Built views.** The pipeline map pages (`docs/pipeline-map/index.html`, `www/library/pipeline-map.html`) are not committed ([ADR-036](../../wiki/decisions/ADR-036-generated-views-not-committed.md)). The `pipeline-map` check (`build_pipeline_map.py --check`, a job of its own and one of the quick docs checks) draws both in memory and fails on a stale graph or a page that does not build; it compares no bytes. `make map` writes them to look at; the site build writes its own copy. Since 2026-11-25 the site's generated JSON is built the same way: `www/data/tables-browser.json`, `layout-index.json`, `layout-index-cats.json` and `wiring-inventory.json` (`www/scripts/site_views.py`). Their checks keep their names (`tables-browser`, `layout-index`, `layout-index-cats`, `wiring-json`) and build the JSON in memory and run its own checks instead of comparing it with a committed copy; the two layout checks also compare each committed PNG's render stamp with its current inputs. `make site-data` and `serve_portal.py` write the files into `www/` for the local preview.
- **Job stamps.** Each job runs under a trace hook (`tools/audit/traced.py`) that records the files its Python processes opened, probed and listed. A job whose recorded reads are unchanged since its last pass prints `<job>: current, skipped` and is not run again, so an edit re-runs only the jobs that read the file. A job that ran bash, node or a writing git falls back to the folders `tools/audit/check_stamps.py` declares for it. `python3 tools/audit/check_stamps.py why <job>` says why a job ran. A manifest job's key holds a digest of its own `checks.toml` entry and the git refs its `git` field names, so editing one step reruns its job and no other, and a step whose `git` names `head` reruns after every commit. Each step starts with `git = ["head", "base"]`; a step whose trace shows it reads git only through read-only git commands (which the stamps replay at compare time) and nothing under `.git` may drop them, with the reason in a comment (`phase02`, `devices`, `parked`, `railroad-facts` and `sml-invariants` so far). `HART_CACHE_DIR` and `HART_GUARD_JMRI_RUNNING` are in every job's key: the first picks the cache folders a job reads, the second the answer the table writers and their tests skip or refuse on; an edit to `check.sh` or `tools/pipeline/manifest.py` reruns every job. Every job's stamp is checked in one `check_stamps.py current-batch` process before any job starts, and a current job is never started; when that process fails, every job runs, none records a stamp, and the output says why. A unit job whose tests skipped records its stamp too, with each skipped test's id and reason in its key; what a test skips on (a tool `shutil.which` does not find, a package, a file, a git ref) is an input like a file it read, so the job runs again when that changes. Stamps are in `<main checkout>/.cache/hart/check-stamps`, shared by every worktree on the Mac and by `make remote` runs of `main` (other refs on the Windows box: see below). `make panels` steps are stamped the same way (`python3 tools/schematic/panel_stamps.py why <step>`).
- `make static` runs the `static` group less the `panels-*` jobs (`CHECK_ONLY` built from `manifest.py jobs check --group static`): about 20 s warm, run before each push so a `make remote` run does not fail on a rule check.
- `FULL=1` runs everything and records the stamps; with `CI` set nothing is skipped or recorded, except in the two CI modes below. `CHECK_ONLY=<regex>` runs only the jobs it matches.
- **Timings.** A local run (not CI or an audit run) appends each step-manifest job's seconds and result (ok, failed, skipped: its stamp held or it printed SKIPPED) to `step-timings.tsv` in the shared cache, runner `check`, mode `cold` only with the schematic cache off or still empty after the run; `make panels` writes to the same log. `make timings` refreshes `docs/pipeline-map/timings.json` from it ([schematic panels](../../wiki/pipelines/schematic-panels.md)).
- **CI skips what main covered.** Main's push run runs every job with `CHECK_RECORD_TO` and saves the stamps of the jobs that passed in the Actions cache, keyed on its commit. A pull request run restores the stamps for its merge base and runs `check.sh` with `CHECK_SKIP_FROM`: a job whose inputs are byte-identical to that pass prints `<job>: current on main <sha>, skipped`, and every other job runs. `tools/ci/stamp_gate.py` runs everything, and logs why, when the stamps are missing or for another main commit, the runner image, Python, git or bash differs (not the image build number, which varies between runners), the plugin pin changed, the change touches `check.sh`, `check.yml`, `tools/pipeline/manifest.py` or the stamp code (not `checks.toml`: each job's key holds its own entries), the pull request has the `full-ci` label, or one of its commit messages has `[full-ci]` (add the label, then re-run the job). Jobs that cannot be stamped (a check that printed `SKIPPED`) and jobs whose key holds HEAD (the checks whose `git` names `head`, and `unit-hosts test_redeploy_commit`) always run. Each pull request run that passed keeps the names of the jobs it skipped (the `check-skips` artifact, `stamp_gate.py record-skips`, from `check.sh`'s `CHECK_RESULTS_TO` file). A weekly scheduled run checks main in full and then fails, with `::error::wrong skip?` lines, when a job that a pull request run of the last 8 days skipped fails in it (`stamp_gate.py check-skips`), so a stamp key that leaves an input out shows within a week.
- **Panels.** Every output drawn from the schematic is checked by the steps of `make panels CHECK=1`, not a copy of them: the `panels` step of `checks.toml` stands for one job per step of `tools/pipeline/panels.toml`, `panels-<step>`, which runs that step's command with its `check_args` (ADR-037 stage 6). A check writes nothing, so the jobs run side by side in any order; `make panels` still runs the steps in file order for builds, with its own stamps. Each job is a traced Python job like any other: skipped while its reads match its last pass, locally and on a pull request run against main's stamps. Its key also holds its own `panels.toml` entry and the `panels` step's, the step's outputs and make panels' code (`panel_stamps.CODE`) whole, read or not, and the merge base for a step that publishes (`schematic`). The deploy gate proves G4 from main's `panels-tables` job (`tools/hosts/deploy/ci_pass.py`). With `HART_TABLES` set nothing is stamped and the table steps read that file. Without the plugin a step fails (`SCHEMATIC_REQUIRED=1`, as in CI).
- **Pyflakes.** The `ruff` job runs `tools/audit/check_ruff.py`: ruff's F rules only (undefined and unused names, unused imports, f-strings without placeholders), no style or formatting rules. `ruff.toml` at the root lists what is excluded (vendored code, `archive/`, the parked features, Jython scripts that do not parse as Python 3) and the per-file ignores (F821 in Jython scripts, whose names come from JMRI or from `execfile`; files other branches are changing, to remove after they merge). Ruff is pinned in `requirements.txt`; the check uses that version from the main checkout's `.venv`, else from PATH, and fails when neither has it. CI installs the pin (`check_ruff.py --pin` prints it), and `make remote` installs each pinned version once with uv into `~/.cache/hart/ruff/<version>` on the Windows box and puts it first on PATH for that run; a failed install there is a warning, and the ruff job then fails with the reason. On the Mac: `.venv/bin/pip install -r requirements.txt` in the main checkout. `.claude/hooks/check_after_edit.py` runs the same check on each `.py` file an agent edits (a file git ignores is skipped, as the whole-repo run skips it): findings block the edit, and a missing ruff is one line that does not block. The stamp falls back to its declaration (every `.py`, `ruff.toml`, `requirements.txt` and the `.gitignore` files), since ruff is not Python.
- **File sizes.** The `py-sizes` job (`tools/audit/check_py_sizes.py`) fails when a `.py` or `.js` file over 800 lines, or a `.sh` file over 500, grows past its row in `tools/audit/py_sizes.csv`, and when one crosses its limit with no row; a listed file that shrank, fell to its limit or is gone passes with one note until `--update` tightens the list; `--update --accept PATH` raises or adds a row by name. A file at 90 percent of its limit (720 lines for `.py` and `.js`, 450 for `.sh`) with no row gets a `WARNING` line and the job still passes; it shows when the job runs, not when its stamp skips it. `archive/`, `external/`, `reference/`, `tools/cats/src-repo/`, the parked features and any `node_modules` folder are not measured.
- **check.sh stays one file** (decided 2026-11-25, size sweep group F). At 585 lines (2026-11-25; 600 after `job_status`, the same day) it is: start-up (`HART_TABLES`, the docs-only path, the schematic cache, submodules, the plugin pin) 84, run modes (stamps, CI record and skip, results, the audit) 86, the manifest loader (`manifest_lines`, `has_step`) 47, the scheduler (`later`, `read_verdicts`, `start_jobs`, `job_status`, `collect`) 198 (213 with `job_status`), the job runners (`unit`, `run_line`, `run_check`) 40, the queue (panels first, the Layout Editor job, the unit test loops, the portal) 122, and the last 8. No part moves into a sourced file. The scheduler and the loader read and set the run's globals (`names`, `cmds`, `pids`, `verdicts`, `JOBS`, `STAMPS`, `RECORD`, `AUDIT_FAILS`, `MANIFEST_JOBS`, `fail`), so a sourced file would not stand alone. Every job's stamp key hashes `tools/check.sh` by name (`check_stamps.ALWAYS`) and `stamp_gate.MACHINERY` lists it: a second file would have to join both, rerunning every job once locally and in CI, and the tests that read `check.sh`'s text (`test_stamps_batch` takes `read_verdicts` and the `.cache` block out of it, `test_stamp_gate`, `test_check_sh_tables`, `test_check_docs_only`) would read two files. ADR-037 moves job lists into the manifest, not the scheduler. Its row in `tools/audit/py_sizes.csv` (over the 500-line limit for shell) means it cannot grow without an accept by name: the `job_status` fix was accepted that way (585 to 600).
- **No plugin, no pass.** `check.sh` and `make panels` set `SCHEMATIC_REQUIRED=1` unless it is already set, as CI does: a schematic check that cannot load the schematic-maps plugin fails instead of printing SKIPPED. `SCHEMATIC_REQUIRED=0` lets those checks skip. A job that still printed SKIPPED (the owner's plan file is not on the machine, say) is named on one line at the end of the output.
- Logged times: a warm local run takes about 40 s, a full run 2 to 5 min. Grep earlier output (`--- job (Ns)`) before re-running just to time it.

## make remote

`make remote CMD="./tools/check.sh"` (or `tools/hosts/win_run.sh -- <cmd>`) runs a pushed branch on the Windows box's WSL. `.wslconfig` there caps it at 8 of the box's 16 threads, and each run gets its own worktree, so several at once are fine. Every run's whole output, stderr included, is saved on the Mac in `<main checkout>/.cache/hart/remote-logs/<ref>-<time>.log` (the newest 20 kept, `WIN_RUN_KEEP_LOGS`), and the run ends with each `--- <job> FAILED` line and then `log: <path>`, so a caller that keeps only the tail still sees which jobs failed and where the rest is.

- Use it for a full `check.sh`, test suites and panel rebuilds. Iterate on single tests locally.
- **Stamps per ref.** A run of `main` uses the box's shared stamp folder (`~/hart/.cache/hart/check-stamps`); any other branch gets `check-stamps-by-ref/<branch, sanitised>-<hash>` beside it (a detached commit: its sha), copied from the shared folder on its first run, so parallel runs of different branches no longer overwrite each other's stamps. A copied stamp is skipped only when its key and every read-set hash match the run's checkout, and a folder untouched for 14 days is removed at the start of a run.
- A command with `$` in it goes through `tools/hosts/win_run.sh -- bash -c '...'`, because make expands `$`.
- Exit 3 means the operating flag is set and the box is down: run it on the Mac.
- Never use it for `panelpro-test`, screenshots or deploys.
- When the Mac is busy (load above about 8, or several sessions running checks), run `make remote` in the background beside Mac work, and have subagents run their full checks and suites through it.
- The Mac has 8 cores. Keep CPU-heavy local work to about 2 jobs at a time per session.
