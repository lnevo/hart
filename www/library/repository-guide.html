Inside the Repository

Everything that runs this railroad, from the JMRI tables to this website, is kept in one public git repository. This guide shows how it is laid out, where each fact lives, how the separate projects attach to it, and how a change reaches the layout.

The repository is github.com/lnevo/hart. It holds the JMRI tables and panels, the CATS dispatcher desks, the car records, the wiring documents, the scripts that build and check all of them, the decision records, and the source of this website. Six smaller projects with their own repositories are attached as submodules. The computers on the layout are installed from it, and none of them is a git checkout.

01The overview

The Mac holds the master copy. A change is made there, checked, merged into main and then deployed. Two deploys leave the repository: one installs the JMRI and CATS files on the layout computers, the other publishes the website. A few things are made on the layout itself during a session, such as a PanelPro Store or the positions of cars, and those come back into the repository by a pull command before the next deploy.

Inside the repository, files fall into three kinds:

  • Sources of record. The one file that owns a fact, such as the tables file, the name map or the car repository. A change starts here.
  • Tools. Scripts that build copies from the sources, check that everything agrees, and deploy.
  • Generated files. Copies made by the tools, such as the two CATS desks, the crew documents and the website's data. Nobody edits these by hand; a fix goes into the source or the script that made them.

02The top-level folders

There are ten folders at the top. Each has one purpose, and a file that does not fit any of them is a sign it is in the wrong place.

FolderWhat it holds
jmri/The layout's JMRI files: the tables file, the Operations Pro files, the layout data, and the scripts that build and check them. Also the icons and web pages JMRI uses.
cats/The CATS dispatcher desks only: the one drawn panel, the two desks made from it, and their scripts.
ops/Operations: the car repository and its tools (ops/hart-ops/), station maps, car-card intake batches, and runbooks for the parts that run outside JMRI.
docs/Every document written for the railroad: wiring, CTC, benchwork, JMRI notes and the crew publications. docs/INDEX.md lists them, newest first.
www/The source of this website and the scripts that build and publish it.
tools/Repository-wide tools: the checks, the shared library, host and deploy scripts, MQTT helpers and the LCOS mimic.
external/The six submodules, and the STS data folder.
wiki/Decision records, the live status of the railroad, and one page per pipeline.
media/Photos, video and research material. Kept on the Mac, not in git.
archive/Retired files, kept for reference. Nothing in it runs.

Three files sit at the top as well: README.md for people, AGENTS.md with the working rules for every AI tool, and a Makefile whose short commands (make lists them) run the real scripts.

The switch files show how this works in practice. Moving a switch's legs is a change to one row of switch_legs.csv, then a run of the generators. If the Layout Editor, a CATS desk and the USS board then disagree, the check fails and names the switch and both files.

04The layout tree

Most of the railroad's control lives under jmri/layouts/hart/. There is one layout, hart; when the upper levels are added, the unit is the level, recorded in the level column of the switch files, not a second layout folder.

FolderWhat it holds
output/tables.xml, the one tables file, with all three panels in it
data/The name map, switch files, block lengths, control points, and HART's settings for the STS-to-JMRI refresh
operations/The six Operations Pro files
scripts/About sixty scripts that build, repair and check the tables, plus the ones that run inside JMRI
ctc/, dispatcher/The USS CTC machine's icons and guide; the Dispatcher System's options and train files
anyrail/The AnyRail track plan export the first panels were built from

Two kinds of Python script live side by side here. Most run on the Mac in ordinary Python and read or write the files. About twenty run inside JMRI itself, from the Start Up list on each computer, such as the panel status and the STS car refresh. Those use JMRI's built-in Jython, which is Python 2, so they import nothing from the repository's shared code and run on any computer with JMRI installed.

cats/ works the same way on a smaller scale. One panel is drawn in the CATS Designer, HART_Digicon.xml. A script writes the two desks the dispatchers use from it, CTC and ABS, and another validates them. make desks runs both.

05Shared code

The Mac-side scripts share one small library, hartlib, in tools/hartlib/. It has three parts:

  • paths names every file the tools use: the tables file, the name map, the wiring table, the layout folders. A path always points into the checkout the script sits in.
  • tables loads and saves tables.xml. A load followed by a save with no edit writes the same bytes JMRI wrote, so a script that changes one sensor changes one sensor in the diff. It also knows the file's traps: sensors and turnouts split over several sections, every block written twice, two kinds of mast. A save refuses while PanelPro or CATS is open.
  • hosts holds the MQTT broker and the address of each layout computer, read from the environment, then a local settings file, then the defaults. The shell scripts read the same settings in the same order.

The library is not installed. Each script finds it with two lines that walk up from the script's own folder, so a script always uses the copy beside it, and moving a script needs no edit. That matters because every change is made in a separate working copy (see Making a change); an installed library would point every copy at one of them. The scripts that run inside JMRI never import it.

06Submodules

A submodule is another git repository checked out inside this one. The hart repository records which commit of each one it uses, so a fresh clone with git clone --recurse-submodules, or make submodules after a pull, puts every one at the right version. All six live under external/ and all six are public.

FolderWhat it isHow it connects
lcos-bridge/Firmware for the Arduino that listens to the LCOS radio nodes, and the bridge that turns their messages into MQTTThe bridge runs on the Windows PC and publishes to the broker on the Pi
sts-docker/The STS traffic simulator packaged to run in DockerThe Pi runs its release build as the live STS; the Mac runs a copy for testing
sts-plugins/Addons for STS: the track scale, coke orders, the JMRI refresh and HART's own settingsBuilt into the STS image
sts-helpers/Seeding, warm starts and switch lists for STSRun on the Mac, fed from the car repository
model-railroad-skills/Skills and plugins for AI coding agents: JMRI panels, signals, MQTT, CATS, STS, Operations Pro and car cardsInstalled into the AI tools; nothing on the layout uses it
jmri-cs105-roster-sync/Copies the JMRI roster into the TCS CS-105 command stationRun from tools/ops/ after a roster change

The rule for what becomes a submodule: a project another modeler could use on their own layout. Those projects carry nothing specific to this railroad. HART's values live in the hart repository and are loaded as settings, such as the STS-to-JMRI names in jmri/layouts/hart/data/sts_jmri_ops_settings.json, or kept in one clearly named place, such as the hart_layout plugin in sts-plugins. A test in sts-plugins fails if a HART name appears anywhere else.

The rule also works the other way. The car tools, hart-ops, were a separate repository until November 2026. Nearly everything they read and write is in hart, so every change needed two pull requests, one in each repository. They now live in ops/hart-ops/, and their tests run with the rest.

Two folders look like submodules and are not. The STS data folder in external/ holds the simulator's database, backups and photos, outside git. The research scans are a private repository of their own, cloned separately into media/.

07What stays out of git

Some files are too large, too private or too changeable to track. They stay on the Mac, beside the repository, and the tools know where to find them:

  • Photos and video in media/, and the car photos in their own folder under ops/. The website build resizes them into the published site.
  • The STS database and backups in the STS data folder under external/, with copies of the live Pi data pulled there after each session.
  • CATS itself: the release and its source are downloaded by scripts in tools/cats/.
  • Local settings such as tools/env/hart.env, and any credentials.

A check, also run as a git hook before each commit, stops a private or ignored file from being added by mistake. Another reads every tracked file, Office documents included, for text that must not be published.

08From the repository to the railroad

Three computers run the layout. The Pi is production: it runs JMRI, the MQTT broker every client talks to, the CATS desks and the live STS. The Windows PC runs JMRI, CATS and the LCOS bridge. The Mac holds the repository and is where changes are tested and accepted before they reach the Pi.

The layout deploy

tools/hosts/sync_hart_package.sh builds a package from the repository for each computer and sends it: by rsync to the Pi, as one archive to Windows. The package is a subset, with the tables, panels, Operations files, JMRI scripts, CATS desks and launchers, and none of the documents or the website. On each computer it installs into JMRI_UserFiles, and every computer's JMRI loads its tables from there, so an install looks the same everywhere. Each install leaves a stamp naming the commit it shipped; make deploy-status reads them back.

What comes back

The repository is the master, so anything made on the layout has to be brought back before the next deploy replaces it:

CommandBrings back
make tables-pullA PanelPro Store, into tables.xml
make ops-pullThe Pi's Operations Pro state after a session
make sts-pullThe live STS backups and a database dump

The deploy stops if a Store has not been pulled. Pulled files are committed like any other change.

STS on the Pi

STS is the one exception to the package deploy. The Pi has its own clones of sts-docker and sts-plugins, and tools/hosts/pi_sts_update.sh updates it by a git pull and a rebuild there. A change is tried in a sandbox first, then on the Mac's copy, where it is accepted, and only then on the Pi.

The website

www/scripts/deploy_hartrailroad.sh builds the site from tracked files only, copies in the documents and pictures listed in www/scripts/published-files.json so the site holds no copies of its own, resizes the photos, checks every link, and publishes. It stops if the build has far fewer pages or photos than the last one.

09Making a change

The main checkout on the Mac stays on main, for pulls and deploys only. Each task gets its own working copy, a git worktree, made by make wt TOPIC=<topic>. It sits in .claude/worktrees/<topic>/ on its own branch, with links to the photo folders the website build needs. Several tasks can run at once without one switching the branch under another.

  1. Edit in the worktree. Scripts change the tables file only while PanelPro and CATS are closed.
  2. Check with ./tools/check.sh: about thirty checks and test suites, from the tables and signal logic to the car tools and the website links.
  3. Load it for real with make panelpro-test when the tables or panels changed. It opens the tables in PanelPro on the Mac and reports any error.
  4. Open a pull request. GitHub runs the same checks on a clean copy. main accepts a change only through a pull request whose checks pass.
  5. Merge and deploy. The worktree is removed automatically once the merge is half an hour old.

Hooks in .claude/hooks/ back these rules up for the AI tools. They stop a commit or push to main, an edit in the main checkout, and any command that writes the tables or deploys while PanelPro or CATS is open. Cursor runs the same checks through its own hook file.

10Decisions and documents

Decisions are written down in wiki/decisions/ as short records, ADR-001 onward. Each says what was decided, why, and what it replaced, and a later change is added as a dated amendment. The layout of the folders above is ADR-007; the one tables file is ADR-008; the shared library and switch files are ADR-021.

The rest of wiki/ is the railroad's current state: STATUS.md for what is live, one page per pipeline in wiki/pipelines/ for how each thing is built, and a list of what is waiting on a person. Documents written for the railroad go in docs/. The working rules for AI tools are in one file, AGENTS.md; the Claude and Cursor settings point to it, and a check fails if it names a path that no longer exists.

A good place to start reading is the wiki home page, wiki/home.md. It links to the decision records, the live status, the pipelines and every document.
