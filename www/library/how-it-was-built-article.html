How the Railroad Got a Repository: Building HART with AI Agents

One person, one layout and a crew of AI helpers. A plain-language look at how the project is kept in a repository, who is allowed to touch what, and what went wrong on the way.

Since the first week of August 2026 I have run the HART project as a repository, with AI agents doing much of the legwork and a few rules keeping them honest. If you have ever lost track of which copy of a spreadsheet was the real one, you already know the problem this solves.

The railroad's traffic, the cards and the session paperwork, is told in the operations story. This page is about something else: the working method, how the files are laid out, and the rules.

Chat is a scratchpad; decisions live in the wiki.

01The railroad has a repository

A layout is a lot of files that have to agree with each other. The software that runs it, JMRI, keeps its turnouts, blocks and signals in a single XML file. The dispatcher's control panels are a drawing file. Then there are the wiring documents, the website you are reading, the 3D-print files for the benchwork, and a wiki of notes. Change one without the others and something quietly stops working.

A repository (repo for short) is a folder where every change is recorded. A commit is one saved snapshot with a note saying why. A branch is a side copy of the whole folder where work can happen without disturbing the main line; when it is good, it is merged back. Anyone can see what changed, when, and go back.

HART's first commit was on August 7. By October 31 there were about 675 commits, made on 47 different days. The folder layout is itself a recorded decision. Each of those decisions is an ADR, an architecture decision record: a short page saying what we decided, why, and what it replaced. There are 13 so far. One of them, ADR-007, sets the top-level folders: the JMRI data, the CTC panels, documents, the website, tools, the wiki and an archive for retired material.

02One source of truth per thing

Most of the decision records say the same thing in different words: there should be one real copy. Three of them were reversals of something I had set up myself.

Three reversals

  1. One tables file (ADR-008). I had a working copy of the JMRI tables beside the real one. That meant two files to keep in step, and changes could reach only one. Now there is one file, and git branches do the job the spare copy used to do.
  2. One panel save, two desks (ADR-012). The CATS control panels had grown to six files. They had drifted: the desks held edits the source did not, so a rebuild would have undone them. Now one Designer save is the only file anyone edits, and a script writes both dispatcher desks from it. Nobody edits a desk by hand.
  3. One car repository (ADR-013). Three tools held different cars. There is now a single repository that holds the whole fleet, and the others are fed from it.

Documents got the same treatment (ADR-010). Anything we create lives in one folder, and the website holds no copies. A list names each published file and where it comes from, and the site build copies them.

Then there is the problem of the AI forgetting. An agent starts each session knowing only what is written down, so anything not written down is lost. That is why the pull quote above is the first rule in the instructions file. The wiki has a live status page and a separate dated log. The status page says what is true today; the log says what happened and when.

03Repos within the repo

Some of the work belongs to projects that stand on their own. A submodule is a pinned snapshot of another repo, kept inside this one. The main repo records exactly which version it uses, so nothing shifts underneath it unnoticed, and each submodule keeps its own history and rules.

Four of them are public, and you can read them:

  • LCOS_ESP32_MQTT_Client, the bridge that links JMRI to the layout's signal and turnout electronics (see Electronics & the bridge);
  • sts-docker and sts-docker-helpers, for running the traffic simulator;
  • model-railroad-skills, covered in section 05.

A fifth, private repo holds the car inventory and the card and waybill tooling.

04The agents and their fences

All the rules live in one file, AGENTS.md, and every tool I use reads it. It holds the commands, the list of things never to do, and a close-out routine for any task that changed files: update the wiki, commit on a branch, push, test, deploy, then report what was done.

The day-to-day AI is Claude Code, which took over in mid-October from Cursor. Cursor did most of the early work: at least 367 commits are credited to it between August 7 and October 15, and at least 270 to Claude from October 14. Both are named in the commit notes.

Some jobs are handed to a subagent, a helper with its own written instructions and one bounded task. I have five, kept in a folder of their own. Four are read-only: one traces why a signal or panel behaves as it does, one audits the repo for dead code and stale notes, one reviews the website through a named lens, and one researches history and sources. The fifth builds website pages and may edit only the website folder. None of them commits, pushes or deploys. The main session does that, and checks the result.

The fences themselves are small scripts called hooks: a hook runs just before the AI executes a command and can say no. The first, main_guard.py, runs in every session. It stops a commit or a push to the main branch, a force-push, and an admin merge that would skip the required check. It asks me first before anything that would send a command out to the layout. I have also let agents merge a pull request once the required check passes; GitHub refuses it otherwise, and the admin-merge block still applies.

The second, subagent_guard.py, applies to subagents only. It reads each shell command and refuses the ones that save to git history, publish the website, reach another machine or act on the railroad, and tells the subagent to report back instead. It matches where a command starts, so a subagent can still search for those names. The file says of itself that it is "a guardrail against mistakes, not a security boundary", and I take that literally. Read-only for the four reading agents rests partly on their written instructions, too.

Every pull request also runs tools/check.sh, a set of automated checks on the tables, signals and the agent instructions themselves.

These arrived late

None of this was there at the start. The only automated workflow before October, added on September 8, published the website. The checks on every pull request, both hooks and the five subagents arrived on October 31, after several of the mistakes in section 06 had already happened. That is part of the story.

05Skills and read-only tools

A skill is a written guide the AI loads when a topic comes up, so it works from the right notes instead of guessing. An MCP (Model Context Protocol) is a plug-in that gives the AI a tool it can call. Both live in a public plugin, model-railroad-skills: six skills and two tools, for anyone running JMRI, CATS or STS.

The skills cover editing JMRI panel files safely, signal mast logic, the Dispatcher System package, JMRI's own messaging, CATS, and running STS in Docker. The two tools can look but not touch. One reads what JMRI reports through its web interface, using only requests that fetch information. The other listens to the layout's message traffic for up to 30 seconds and shows what it hears.

The rule for adding anything is to check it against the software's own source and record which version. That check has paid for itself. When the skills were checked against JMRI, it corrected our own wiki: the way JMRI assigns signal-mast slots at a buffer stop is its normal behaviour, not the hack we had written it up as.

I also decided what not to build. There are no tools for serial ports, flashing the electronics, deploys or CATS. Anything that can change the railroad stays with a person. The caveat is honest: the JMRI tool has only been tested against a stand-in server, and the message tool only against a local test broker. Neither has run on a live layout. The plugin holds nothing specific to this railroad.

06What went wrong

Five things, picked because each one left a rule behind.

Five mistakes and what they left

  1. Signals, three ways. I tried a custom signal set, then a stock set with some aspects switched off, then settled on plain stock (ADR-006, replaced by ADR-011). The middle one showed false Stops that alternated with Approach all the way back up the line behind a real Stop. Stock beat clever. (How the signals work)
  2. Patching JMRI. In August a startup wrapper patched JMRI's Dispatcher System so it would run on this layout. It needed its own fixes in turn, including one by August 22 for a syntax error caused when one of our settings leaked into JMRI's shared scripting engine. The wrapper was gone by September 1. The rule now is to repair the data, not the package, and the wiki keeps a list of those repairs.
  3. Trains running backwards. On August 18, trains dispatched automatically kept running the wrong way, and we hunted through the facing logic for the cause. The software's answers were correct all along. JMRI shares one throttle per locomotive address, so a phone throttle holding the same locomotive, or even picking it up again, sends its last direction and flips it. The rule now is hands off the phone throttle during a dispatch.
  4. A boot script moving points. On August 31 a startup script meant only to light status lamps on the panel was replaying remembered turnout states, and that was moving points. It now reads state and nothing more, and the rules forbid launch scripts from commanding turnouts.
  5. Two sessions, one folder. Run two sessions in the same checkout and one can switch the branch under the other, so its next commit lands on the wrong branch. On October 31 the guard hook and a rule landed together: each session works in its own folder and stages files by name.

07Where the human stays

I decide. I run the layout and I approve what goes out. The agents read, trace, draft and build pages and files; they do not run the railroad. The bridge to the layout electronics runs in a window where I can see it, and agents do not start it.

A repository does not run a railroad. What it does is make the paperwork honest, so that when something is wrong I can find which copy to trust, and when a helper makes a mistake, the damage is small and recorded. The next step is the same as the last one: write the rule down where every tool will read it.
