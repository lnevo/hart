Bringing the Railroad Together

How scattered projects became one repository for the layout, the research and the website, and how AI helped along the way.

The railroad did not start in a repository. The story, the research and the first software came first, with AI in them from early on, and each piece lived wherever it was made. In August 2026 I set out to bring them together for three things: the railroad, the research and the public view.

The railroad's traffic, the cards and the session paperwork, is told in the operations story. This page is about the rest: where the pieces came from, how they were gathered, and the rules that keep one place trustworthy.

Chat is a scratchpad; decisions live in the wiki.

01Before the repository

AI was part of this railroad long before August. The research started in early 2025, and about April is the first solid reference I can point to. ChatGPT generated just about all of the document files. All of the fictional short stories were drafted by AI. The logo is AI-generated. The track plan was settled in July 2025, and the Build page has progress photos from February 2025 on. The 2022 tabletop layout before it saw little AI work.

I stayed with ChatGPT for a long time, until I began using Cursor, an AI code editor, to edit the LCOS project, the software behind the layout electronics. Cursor then helped with the layout-editor work that came out of AnyRail, later CATS, and the rest. Claude took over the consolidation and some of the other work as I started testing outside Cursor.

The operations work is another place AI helped. In the operations story, which I also wrote up for The Cannon Ball in Summer 20266, it helped build the car cards by matching photos to the roster, and it ran the heavy iteration when tuning the traffic simulation.

So by the summer of 2026 the project was real and busy, but it was scattered: documents and research in their own folders, the fiction in its drafts, control software for the layout in one project, the traffic simulation in another, car records, the bridge to the electronics, and the website. Each worked on its own. Nothing made sure they agreed.

02August: bringing it together

A repository (repo for short) is a folder where every change is recorded. A commit is one saved snapshot with a note saying why. A branch is a side copy of the whole folder where work can happen without disturbing the main line; when it is good, it is merged back. Anyone can see what changed, when, and go back.

This repository's first commit was on August 7, 2026. By August 31 the other projects (the traffic software, the car data and the website) had been gathered in beside it. The research and the website's own domain followed in October.

The folder layout is itself a recorded decision. Each of those decisions is an ADR, an architecture decision record: a short page saying what we decided, why, and what it replaced. There are 13 so far. ADR-007 sets the top-level folders: the JMRI data, the CTC panels, documents, the website, tools, the wiki and an archive for retired material. Most of the others say the same thing in different words, that there should be one real copy: one tables file (ADR-008), one panel save that writes both dispatcher desks (ADR-012) and one car repository (ADR-013).

Documents got the same treatment (ADR-010). Anything we create lives in one folder, and the website holds no copies. A list names each published file and where it comes from, and the site build copies them.

Then there is the problem of the AI forgetting. An agent starts each session knowing only what is written down, so anything not written down is lost. That is why the pull quote above is the first rule in the instructions file. The wiki has a live status page and a separate dated log. The status page says what is true today; the log says what happened and when.

Some of the work belongs to projects that stand on their own. A submodule is a pinned snapshot of another repo, kept inside this one. The main repo records exactly which version it uses, so nothing shifts underneath it unnoticed, and each submodule keeps its own history and rules. The public ones include:

  • LCOS_ESP32_MQTT_Client, the bridge that links JMRI to the layout's signal and turnout electronics (see Electronics & the bridge);
  • sts-docker and sts-docker-helpers, for running the traffic simulator;
  • model-railroad-skills, covered in section 05.

03Three things it serves

The railroad. The tables that describe the layout to JMRI, the control panels, the signals, the bridge to the electronics and the car cards. Signals settled on plain stock behaviour rather than a cleverer set; How the signals work has the reasoning, and Electronics & the bridge covers the bridge.

The research. The sources are kept together with a note of where each item came from. What is fit to share appears on this site: the historic photo archive and the Prototype articles.

The public view. This site. It is published only from tracked files, so what you read here is what the repository holds.

04The agents and their fences

AI helped well before the repository; the repository is where the rules were written down. All of them live in one file, AGENTS.md, and every tool I use reads it. It holds the commands, the list of things never to do, and a close-out routine for any task that changed files: update the wiki, commit on a branch, push, test, deploy, then report what was done. One rule I keep: repair the data, not the package. If a stock JMRI tool fails on this layout, I fix our files and leave JMRI alone.

These counts describe this repository only, as of October 31: about 680 commits on 47 days, at least 367 credited to Cursor and at least 270 to Claude, whose first credit is October 14. Both are named in the commit notes.

Some jobs are handed to a subagent, a helper with its own written instructions and one bounded task. I have five, kept in a folder of their own. Four are read-only: one traces why a signal or panel behaves as it does, one audits the repo for dead code and stale notes, one reviews the website through a named lens, and one researches history and sources. The fifth builds website pages and may edit only the website folder. None of them commits, pushes or deploys. The main session does that, and checks the result.

The fences themselves are small scripts called hooks: a hook runs just before the AI executes a command and can say no. The first, main_guard.py, runs in every session. It stops a commit or a push to the main branch, a force-push, and an admin merge that would skip the required check. It asks me first before anything that would send a command out to the layout. I have also let agents merge a pull request once the required check passes; GitHub refuses it otherwise, and the admin-merge block still applies.

The second, subagent_guard.py, applies to subagents only. It reads each shell command and refuses the ones that save to git history, publish the website, reach another machine or act on the railroad, and tells the subagent to report back instead. It matches where a command starts, so a subagent can still search for those names. The file says of itself that it is "a guardrail against mistakes, not a security boundary", and I take that literally. Read-only for the four reading agents rests partly on their written instructions, too.

Every pull request also runs tools/check.sh, a set of automated checks on the tables, signals and the agent instructions themselves.

The guardrails came later

The repository did not have them at the start. The only automated workflow before October, added on September 8, published the website. The checks on every pull request, both hooks and the five subagents arrived on October 31.

05Skills and read-only tools

A skill is a written guide the AI loads when a topic comes up, so it works from the right notes instead of guessing. An MCP (Model Context Protocol) is a plug-in that gives the AI a tool it can call. Both live in a public plugin, model-railroad-skills: six skills and two tools, for anyone running JMRI, CATS or STS.

The skills cover editing JMRI panel files safely, signal mast logic, the Dispatcher System package, JMRI's own messaging, CATS, and running STS in Docker. The two tools can look but not touch. One reads what JMRI reports through its web interface, using only requests that fetch information. The other listens to the layout's message traffic for up to 30 seconds and shows what it hears.

The rule for adding anything is to check it against the software's own source and record which version. That check has paid for itself. When the skills were checked against JMRI, it corrected our own wiki: the way JMRI assigns signal-mast slots at a buffer stop is its normal behaviour, not the hack we had written it up as.

I also decided what not to build. There are no tools for serial ports, flashing the electronics, deploys or CATS. Anything that can change the railroad stays with a person. The caveat is honest: the JMRI tool has only been tested against a stand-in server, and the message tool only against a local test broker. Neither has run on a live layout. The plugin holds nothing specific to this railroad.

06Where the human stays

I decide. I run the layout and I approve what goes out. The agents read, trace, draft and build pages and files; they do not run the railroad. The bridge to the layout electronics runs in a window where I can see it, and agents do not start it.

A repository does not run a railroad. What it does is keep the paperwork honest, so that when something is wrong I can find which copy to trust. The railroad, the research and the public view now work from one place.
