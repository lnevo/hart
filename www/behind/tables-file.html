The Tables File: One File That Is the Railroad

Every switch, sensor, block, signal and route the railroad has told JMRI about lives in one XML file. Here is a tour of it by the numbers.

What the file is

JMRI, the free model-railroad software that runs this layout, keeps what it knows in "tables". There is a table of turnouts (the switches), a table of sensors, a table of blocks (stretches of track), and so on. When you save, JMRI writes all of them into one XML file. When it starts, it reads that file back, and the railroad is there again.

Ours is called tables.xml. It is about 2.2 MB and 29,068 lines long, and it has 27 top-level sections. It is in the ordinary JMRI format, stored by PanelPro 5.15, the main JMRI program. It holds no connection settings: how JMRI reaches the layout lives in the profile, a separate set of preferences. Everything else is in here, including the three panels you see on screen.

One aside, because it trips people up. JMRI writes the Blocks section twice, a first pass with names only and then the full pass. Count the lines naively and you get 110 blocks. There are 55.

The 639 sensors break down further. Of the internal ones, 192 are section sensors (96 forward and 96 reverse), 69 are Dispatcher System helpers, 260 are CTC panel sensors (13 kinds across 20 columns), 23 belong to Entry/Exit and 9 each do one job.

How the pieces link

The tables are not a pile. Each one points at the next by name, so a detector on the track ends up as a leg of a train's route. The figure follows the chain.

Start at the top. An occupancy sensor reports a train on the track. A layout block (the Layout Editor's view of a block) names that sensor, and a block of the same name carries the paths. Several blocks can share one detector: the yard tracks split into West and East halves, and Track S-1, S-1 West and S-1 East all use "BS S-1". The same goes for OS Switch 37 and Track K-2. That is how 55 layout blocks get by on 43 detectors.

Here is the block for OS Switch 13, trimmed to the parts that matter: 

<block>
  <userName>OS Switch 13</userName>
  <occupancysensor>BS Switch 13</occupancysensor>
  <path block="Track Barn">
    <beansetting setting="Closed">
      <turnout>Switch 13</turnout>
    </beansetting>
  </path>
  <path block="OS Switch 11">
    <beansetting setting="Thrown"> ... </beansetting>
  </path>
  ...
</block>

Read it as a sentence: from OS Switch 13 you can go to Track Barn when Switch 13 is closed, and to OS Switch 11 when it is thrown. (In the file the settings are numbers, and the blocks are named by short codes. I spelled them out.) Add 126 of those and you have the map.

Masts sit at block boundaries. Signal Mast Logic takes two masts and works out what lies between them from the Layout Editor, using those paths. Here is one destination, trimmed: 

<signalmastlogic source="Mast 2036">
  <destinationMast destination="Mast 38LB">
    <enabled>no</enabled>
    <useLayoutEditor>yes</useLayoutEditor>
    <useLayoutEditorTurnouts>yes</useLayoutEditorTurnouts>
    <useLayoutEditorBlocks>yes</useLayoutEditorBlocks>
    <associatedSection>Mast 2036:Mast 38LB</associatedSection>
  </destinationMast>
</signalmastlogic>

The pair creates a section named "Mast 2036:Mast 38LB", which is why the Dispatcher's sections are named after masts. The Dispatcher chains sections into a transit, a whole move from one mast to another via the switches in between. Entry/Exit reuses the same pairs rather than inventing its own.

Switches have a link of their own. This one reports its position through two sensors, one for each side, so JMRI can tell "thrown" from "not yet arrived": 

<turnout feedback="TWOSENSOR"
         sensor1="FB Switch 35 R"
         sensor2="FB Switch 35 N">
  <userName>Switch 35</userName>
</turnout>

Who writes what

PanelPro owns the file. Anything you do on screen, such as moving a mast on a panel, ends up there when you store. A few jobs are better done by script, and each does one thing:

  • A name map turns working names into the public equipment names that appear on this site.
  • Another script places the masts and their heads.
  • JMRI's own Discover tool finds the Signal Mast Logic pairs from the panel.
  • The CTC data generator writes the CTC data, including the 20 columns of code buttons.
  • Validators check that names agree across the file, so a typo does not become a missing switch.

The scripts that edit the file directly run only with PanelPro and CATS closed. Discover is the exception: it runs inside a one-shot PanelPro, with no other JMRI session open, then stores and quits.

The LogixNG

One piece of logic is not a table of things but a little program. A LogixNG (JMRI's newer logic tool) called "Hide windows on start" is listed in the Initialization Table, which is why it runs when the tables load. It has four ConditionalNGs, each with one stock action:

ConditionalNGStock action
Hide WiThrottleWindow Management: hides the WiThrottle window
Hide USS CTCWindow Management: hides the USS CTC window
Hide Dispatcher SystemWindow Management: hides the Dispatcher System window
Hide HART Railroad under CATSRun Script: runs hide_cats_desk_windows.py

The last action calls an ordinary Jython file, described among the scripts. A LogixNG runs wherever the tables load, so it fires under both PanelPro and CATS with no condition of its own. The script does the checking: it looks at how JMRI was started and at the open windows, and if CATS is not running it does nothing. A window action ignores a window that is not there, so if one is missing, nothing happens.

Stock and ours

The format is stock: it is what JMRI itself writes. What is ours is the content: the names, the comments, the yard-ladder turnouts and the data for the CTC machine. The same rule as on the other pages applies, which is to change data before software.
