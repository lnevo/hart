What We Added to JMRI (and What We Left Alone)

Almost everything here is stock JMRI. This page is about the small part that is not, and why each piece is there.

Stock first

If you run JMRI yourself, you will recognise most of what runs this railroad: Basic signal masts, Signal Mast Logic (SML) with its Discover tool, Entry/Exit, the Layout Editor, the Dispatcher System (run untouched), the CTC tool, the web server, the MQTT connection, Routes, LogixNG, and the green and red lamp icons. CATS, the open-source CTC desk, is stock too. None of that is ours, and we do not claim it.

Where the railroad needed something different, the rule was to change data and add small scripts before touching software. The scripts use public JMRI calls, and the JMRI jars themselves are stock. CATS has a few small load-safety overlays. One suppresses a warning, one skips a loopback probe nobody uses, and one guards against an early crash that would otherwise freeze occupancy.

What follows is what we added, and each section starts with the problem it solves. The story of how the software came together is told in Bringing the Railroad Together, so I will not repeat it here.

Two brains, one lamp

The railroad has 23 signal masts out on the layout. Their lamps are driven by small field electronics (the nodes described on LCOS and the Arduino bridge, and listed in the device roster). Those electronics have a signal logic of their own, and JMRI has Signal Mast Logic. Two brains deciding one lamp is a fight waiting to happen. And if a JMRI session crashes while it owns the lamps, they could sit frozen on whatever colour they last had.

So one switch decides who is in charge: JMRI's logic, or the field logic. Nothing exotic is flipped to make it so. Each source-to-destination pair in SML has a stock Enabled checkbox, and the switch ticks or unticks those boxes. On the 23 field masts that is 44 destinations, all moved together. The other 15 sources, with 54 destinations, have no field heads at all. They stay enabled and are left alone. The set of field masts is not hard-coded: the script finds it from the signals the field electronics report.

The join between the two worlds is JMRI's virtual signal heads. SML sets the mast and its heads, and a script listens to the heads. A head only sends a colour once the field has reported that head, so a node that has never reported is not sent a command. The sessions also share one small shared status flag, kept so a newly started session can read it, that says whether JMRI currently has control.

  • Signals ON. JMRI's logic decides every aspect and the script sends each virtual head's colour out to the field. The CATS and USS desks only hold or release masts.
  • Signals OFF. The field logic decides. The script lets go of the heads and copies the field's status back onto the heads and masts, so the panels show what the lamps are really doing.
  • One pair unchecked. The same let-go and mirror, for that one mast only.

Handing over safely

Changing who is in charge while a train is approaching a signal would be rude. So the hand-over is a short routine rather than a flip. To switch JMRI on: hold all 23 masts, wait about three seconds, tick the pairs, release the holds, announce that JMRI is in control, and push the current colours out. To switch it off: hold, wait about three seconds, untick, release the heads to the field, drop the holds, and announce that JMRI is out. Either way the whole thing takes about four seconds, and the masts are held while it happens.

Three short stories show why it is built this way.

Boot

Normally every pair is forced off when JMRI starts. The script then listens for a second. If nobody has control, this session takes it. If another session already has it, this one stays off and disturbs nothing. If the pairs were somehow stored as enabled, a warning appears and the script takes over safely rather than trusting them. Our deploy also ships the field pairs switched off, because Discover writes them on. If an operator turns signals on while another session owns them, the script probes first and then asks "Force override?" before doing anything.

Quit

Closing JMRI runs the same careful steps in reverse: hold, wait, release, announce disabled. It is hooked in through a stock shutdown task, so a normal exit never leaves lamps stranded.

Crash

A crash is the case that matters, because nothing gets to clean up. The bridge sees a status that still says "enabled" and challenges it. A live session answers and the challenge is cancelled. With no answer, the bridge sets the signals to red, waits about three seconds and releases them to the field logic, which carries on.

The operator's handle on all of this is a button on the main JMRI window strip, "SML Enabled" or "SML Disabled" depending on state. It stays available under CATS, on the CTC Panel, where the other windows are tucked away.

Four lamps

An operator glancing at a screen wants four answers fast: is the bridge up, are the switches using feedback, who owns the signals, is the track powered. Four lamps at the bottom left of the HART Railroad panel say so. They are stock icons on a stock Layout Editor panel; the only thing we added is a script that makes them clickable. Amber means a change is under way. Under CATS the lamps are hidden, but the signals button remains.

Lamps that tell the truth

The yards have ladders of tracks, and a dispatcher or yard crew wants to see which one is lined, not which one was last asked for. Ten small triangle lamps sit on the Layout Editor panel, five for each yard ladder: tracks S-R and S-1 to S-4. Clicking a triangle fires an ordinary JMRI Route that lines that track. The one for Track S-1, for instance, sets five real switches.

The part that earns the name: the lit lamp comes from the feedback sensors, not from the command. If a switch did not go over, the lamp does not claim it did. If the switches match no track, no triangle lights. Routes are also disabled while the panel is being painted, so redrawing a screen can never throw a switch, and a test guards that rule.

What gets installed, and how JMRI finds it

Four scripts get installed. One sets up the lamps, the ladder and the clicks. One does the coordination in the second and third sections; its file name is left over from an older purpose. Both run from JMRI's stock Start Up list. The third hides the Layout Editor under CATS, adds Help and Quit buttons and a "HART Dispatcher Guide" Help item. It is run by a stock LogixNG with four actions: hide the WiThrottle window, hide the USS CTC window, hide the Dispatcher System window, then run the script. A small helper also lifts block labels that the Dispatcher's Stage 1 Store buries.

Deploying copies the scripts into the jython folder of the JMRI user files and adds the Start Up entries to the profile. JMRI finds them through its own preference:jython/ path, so the same thing works on every JMRI install. Many other scripts exist, but they run offline to build the tables, not inside JMRI.

The fourth script has nothing to do with running trains, and it is worth being open about. It is a remote-run hook: a small watcher that starts with JMRI and gives us, and the AI agents we work with, a live way to query a running session. Twice a second it looks for a command file in a fixed local place. When one appears, it runs that file as a script inside JMRI and writes back the result or the error.

That is very handy, and it needs care. Whatever is dropped there runs with JMRI's full access, so it can do anything JMRI can do, including move a turnout. The watcher opens no network service of its own; reaching it takes a login on that machine. The project's rules on commanding the field apply to anything sent through it, and the helper agents are blocked from the remote login that would reach it.

Small resources

The rest is files. Two 16-pixel icons are the triangle lamps. The USS CTC panel has 70 generated track icons plus its GUIObjects file: custom track cells for a stock CTC tool. The web home page is a stock copy with one link added, to the traffic simulator; JMRI serves the copy in the user folder before its own. The panel has a background image. JMRI finds all of these through preference: paths.

There are no custom signal drawings and no custom signal system. The masts are stock Basic masts. The Dispatcher files are data rather than code: options plus the traininfo files that stock Stage 1 writes.

Why so small

Apart from the CATS overlays, every item above is either a file JMRI already knows how to look up or a script written against public calls. Keeping the additions that small means that when a new stock JMRI arrives, there is not much of ours in the way. If you run JMRI and want to try any of it, the pattern is the useful part: one honest switch, a careful hand-over, and lamps that report what the layout is doing.
